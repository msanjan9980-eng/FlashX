# Track B: performance log

For the first two days we tuned a Rust program and took it from 56 s to about 0.2 s, in steps that kept getting smaller. What moved it after that was throwing the design away: a C rewrite on the evening of November 1, then one shared index per phase the next morning, which went from 103 ms to 52 ms in a day. We also got things wrong along the way. The board read our AES hash 12 ms slower than our own machine did, so we tried six other hashes before a per-line profile showed the cause: gcc had turned `L < 16 ? L : 16` into a branch (b-114 to b-116). The failed tries are in here too, next to the ones we kept.

Every step from the reference to our final version, with every live-board run we hold an ID for; a row without one gives its commit. The numbers b-14, b-43, b-49, b-61, b-62, b-90, b-96, b-97 have no entry: they left no reading in this log.

How to read this, in plain words:

- K is the organisers' speed score. It grows as T (run time), M (peak memory), S (lines of code) and D (1 + declared dependencies; ours is 1, the standard library only) fall against the reference. Points are the board's speed points computed from K.
- Each table row is one version of the code. Every push runs all four tracks, so a version that stayed in place through later pushes has several board runs: all of them are in its row, in board order, and T, M and points give their range; the first run listed is the push that carried the change, and the rest re-ran the same code.
- b-NN names one of our numbered experiments; KNOWN marks a known technique, OURS our own idea. A D1 miss is a load that missed the CPU's first-level data cache; a mispredict is a branch the CPU guessed wrong. Both are counted with cachegrind on the VM at one worker.

## The last day's redesign (b-110 to b-129)

All box readings here are medians in ms of alternating rounds on our i5-13500 with the official image's gcc 15, the output hash checked on seed 1 and a fresh seed. From b-122 on the output goes to tmpfs, as on the board. "Lost" means measured and not kept. Rows without an internal run ID: the feed keeps only a track's best and latest run, so the organisers' form, commit · Track B, is what we have; the T beside it was read from the board at the time.

**Where b-109 spent its 103 ms.** Setup 4.7, three rounds of scan 22.5 + answers 8.5, merge 2.7. Top-down: retiring 54.5 %, bad speculation 17 %, frontend 10.8 %, backend 17.7 %. 5.09 G instructions, 15.1 M branch misses, 49 M L1 misses. Corpus: 250,000 documents, 36.3 M tokens; 75,747 query terms; tokens: miss 20.8 %, common 45.4 %, rare 30.6 %, phrase-only 3.2 %. Each part answered every query, so small tuning was running out: a new design was needed, not more of the same.

- **b-110, one shared index per phase.** 4 phases of 62.5 K documents. 84.3-85.0 ms, peak 39.2 MB, against 103.15 and 43.5. ## Decisions

The plan's core choices (KNOWN = the known-best technique's version, OURS = our own design), each held or traded with the measurement that decided it:
- Traded in the last day: per-part answers and their merge, for one shared index per phase and a running tally (b-110, box 103 → 84.5 ms). Exact 8-byte keys, for 32-bit tags over AES (b-111), a wrong-answer risk of about 1 dataset in 3,000 (counted in b-128 and b-129), accepted for the second load per token it saves. Memory below the 44 MB cap, for time (b-121).


- 1, map `docs.txt` read-only and never copy it to the heap (KNOWN): held. The mapped corpus costs about nothing in the box's M (b-1).
- 2, look up only the terms the queries use (KNOWN): held, in one table for interning and the probe (b-13), now 7 tags and their values per cache line (b-111, b-118), filled by all workers at once (b-84).
- 2b, one 12-thread pass over document ranges with posting lists in arena blocks (OURS): the pass held; the posting lists were traded. With a posting store one pass could not get under the 43,999,232 B memory cap (b-2), so b-3 decides BOOL queries inside the pass with no store, and b-28 folds every BOOL query per 64-document window. That window was traded in turn by b-68, which folds each triggered query once per 1,024-document chunk from rows and a sorted log of the rarer terms' hits (box T 0.250 → 0.238 s).
- 3, no stored positions, phrases through an inline Aho-Corasick automaton over term ids (OURS): no positions held; the automaton was traded for anchor checks at each phrase's rarest term (b-8), each first filtered by a neighbouring term (b-98; now the term after the anchor, or before it when the anchor ends the phrase), with the anchor the term with the lowest sampled count.
- 4, Rust (KNOWN): traded for C (b-101). The rewrite moved BOOL answering out of the pass into per-part lists and rows, T 0.209 → 0.146 s on the box, then 0.139 s with b-102.

Rejected:
- b-5 (KNOWN): an AVX2 tokenizer; dropped, no gain and S grew by 50 lines.
- b-12 (KNOWN): a document's tokens buffered and their table slots prefetched before probing; dropped, slower on the box than b-11 (0.376 s).
- b-16 (OURS): a parallel query parse over two insert-only sets shared by the workers; the parse got slower on the VM, not faster, and it added 91 lines of S, so no code was committed.
- b-17 (KNOWN): tokenizing 64 bytes at a time with AVX2 class masks, lower-casing in the vector; slower on the VM at 1, 4 and 12 workers and more instructions per docs byte, so no code was committed.
- b-18 (OURS): 16-byte term-table slots holding each term's first 8 bytes; dropped, slower on the box than b-13 (0.378 s).
- b-19 (OURS): per-term document stamps in place of the per-document presence bitset and its clears; dropped, slightly slower on the box than b-13 (0.378 s), with M up 3.9 MB.
- b-20 variant a (OURS): first-id offers only for a worker's first ten matches of a query; read as noise on the box against b-13 (0.378-0.379 s).
- b-20 variant b (OURS): 12-byte BOOL accumulators (count and sum), the multi-trigger stamps kept apart; dropped, slightly slower on the box.
- b-22 (KNOWN): AND queries of rare terms answered by intersecting doc lists instead of per-document triggers; not built, such queries hold 0.9 % of the 10.7 M per-document evaluations at "rarer than 1 in 1,024 docs".
- b-23 (OURS): the worker count capped at 6, 8 and 10 threads in place of all available CPUs; dropped, the box read K 16.17 (6 workers), 16.41 (8) and 17.78 (10) at T 0.44-0.53 s, so all available CPUs stay.
- b-24b (OURS): accumulator slots numbered by query instead of by trigger list; the box read it 3 ms slower, so the slots follow the trigger lists.
- b-25 (OURS): the window path opened to OR-only queries whose cover holds at least 1 document in 128, 256 or 512; dropped, the box read K 19.13, 18.96 and 18.65, so 1 in 64 stays.

Experiments measured only on the build VM and not kept:

- **b-16** (OURS), a parallel query parse over two insert-only sets shared by the workers (lines and terms). The parse got slower on the VM, not faster: the shared, fixed-size term set misses cache on every term, and the parse did not scale from 1 to 4 workers. It also added 91 lines of S, so no code was committed.
- **b-17** (KNOWN), tokenizing 64 bytes at a time with AVX2 class masks, lower-casing in the vector and hashing each token a word at a time. A second variant kept the byte loop and changed only the hash. Both were slower on the VM at 1, 4 and 12 workers, and both ran more instructions per docs byte (cachegrind). The byte loop's FNV multiply costs almost nothing, because it overlaps the scan. No code was committed.
- **b-22** (KNOWN), answering AND queries of rare terms by intersecting doc lists instead of per-document triggers. It was not built, because the VM count showed too little to gain: such queries hold 0.9 % of the 10.7 M per-document evaluations at "rarer than 1 in 1,024 docs", and 3 % at 1 in 256. No code was committed.
